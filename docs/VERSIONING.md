# Versioning and updating

## Kit versions

The kit follows [Semantic Versioning](https://semver.org/). The single source of truth is
`__version__` in `cli/ai_project/__init__.py`; the package version is read from it.

| Change | Bump | Examples |
|---|---|---|
| Breaking: a project needs manual action after `update` | MAJOR (`2.0.0`) | Lock schema change, profile removed, CORE file moved |
| New content or feature, compatible | MINOR (`1.1.0`) | New agent, stack guide, rule, doctor check, CLI option |
| Fix, wording, clarification | PATCH (`1.0.1`) | Typo in a rule, doctor false positive |

Every release adds an entry to `CHANGELOG.md` and gets a Git tag `vX.Y.Z` on git.netsf.fr.
Projects install a tag (`...git@v1.1.0`) so the version is reproducible.

## Updating a project

```bash
pipx upgrade ai-software-engineering-kit        # or: pip install --upgrade "git+...@v1.1.0"
cd my-project
ai-project update --dry-run
ai-project update
git diff                                         # review, then commit
```

Example output:

```text
AI SOFTWARE ENGINEERING KIT - UPDATE

Current Kit: 1.0.0  (project)
Latest Kit:  1.1.0  (installed CLI)

Changes
✓ AGENTS.md - updated
✓ .ai/stacks/python/README.md - updated
✓ .ai/agents/13-observability.md - added
i .ai/rules/testing.md - kept (customised, kit unchanged)
✗ .ai/rules/security.md - CONFLICT: customised locally AND changed in the kit - kit version in .kit-new

! Updated with 1 conflict(s) to merge by hand.
```

## How update decides

The lock file `.ai/kit.lock.json` stores, for each CORE file, the hash of the content **the kit
wrote**. That is the common ancestor for a three-way decision:

| Local file | Kit file changed? | Action |
|---|---|---|
| Missing | – | Written (restored or added) |
| Unmodified (equal to lock hash) | Yes | Overwritten with the new version |
| Already equal to the new version | – | Nothing |
| Modified locally | No | Kept: your customisation |
| Modified locally | Yes | **Conflict**: new version written to `<file>.kit-new`, yours untouched |
| No longer in the kit, unmodified | – | Deleted |
| No longer in the kit, modified | – | Kept, reported (delete it yourself if unused) |

- `--force` resolves conflicts with the kit version and saves yours as `<file>.kit-backup`.
- Project-owned files (context, custom, docs, README...) are never modified.
- `update` replays the selection stored in the lock file (profile, technology, database...),
  so new agents added to a profile in a newer kit appear automatically.
- If the project was generated by a **newer** kit than the installed CLI, `update` refuses and
  asks you to upgrade the CLI.

### Resolving a conflict

1. Compare `file` and `file.kit-new` (any diff tool).
2. Keep what you need. Ideally, move your project-specific part to `.ai/custom/` and accept
   the kit file as is.
3. Delete `file.kit-new`. The next `update` will not flag the file again unless the kit
   changes it again.

## CI

```bash
ai-project update --check   # exit 1 when the project is behind the installed kit
ai-project doctor --strict  # optional: warnings fail the pipeline too
```
